# MHI2 无线 CarPlay：开发历程与实现说明

维护与后续集成：omonob

本文说明我们怎样把无线 CarPlay 接入既有 MHI2，以及后续怎样解决连接、画面、原厂界面和交付中的问题。本文不公开具体帧率档位、关键帧间隔、画面坐标、分辨率或物理尺寸参数，也不包含车机地址、密码、配对密钥和 SDK 许可。

时间线根据团队提供的项目回顾整理；技术章节依据最终保留的代码、交付材料和测试记录说明。章节顺序是实现依赖关系，不表示每一个后续修订都发生在某个早期日期。

## 二、为什么有线能用，不代表无线只需要换个入口

有线 CarPlay 已经替我们完成了许多基础工作：手机通过 USB 接入、原车设备识别、会话生命周期、音视频接收、触控和退出处理。无线接入失去了这个天然的 USB 设备入口，因此要另外补齐发现、引导和会话接管，同时继续让原车认为它正在处理一个正常的 CarPlay 应用。

我们把问题拆成三个层面，而不是混成一个“连接成功”标志：

- **链路可达**：蓝牙和 WLAN 能否把手机引导到车机，接收端是否已经准备好。
- **会话成立**：配对过、看见设备卡片、点击连接、接收端接到会话，是不同事件。
- **应用可用**：中控是否收到正确视频、音频是否连续、触控能否回传、退出和重连能否正确清理状态。

“看见手机”只证明第一部分信息已经出现；“音乐有声音”也不能单独证明画面和主屏会话已经正常。

## 三、最终链路的分工

```text
iPhone
  ├─ 蓝牙发现、配对和连接引导
  │      └─ 原厂蓝牙进程 + 受限无线接入层
  └─ WLAN 上的 CarPlay 会话与媒体
         └─ 无线接收端
              ├─ 主屏视频 → 原有解码/显示能力 → 原厂 CarPlay 界面
              ├─ 普通音频 → 既有音频通路
              ├─ 触控与媒体控制 ← 原厂 HMI/输入适配
              └─ 仪表衍生通路 → 地图、镜像、导航卡片
```

仪表衍生通路不是无线 CarPlay 本身成立的前提。中控无线运行正常之后，仪表地图、镜像或其他信息仍然需要各自的输入、状态和消费链路。因此我们没有把“中控已连接”当作“仪表所有功能都已经同步”。

同样，这项工作没有把普通音频接入等同于新增环绕声、空间音频或改造功放光纤路由；这些是另外的项目边界。

## 四、蓝牙引导：把无线入口接到原厂蓝牙进程

### 1. 包装原厂进程，而不是替换整个蓝牙系统

`btstack_wrap.sh` 保留原厂蓝牙程序作为实际执行目标，只在本项目的无线功能被允许时，为该进程加载相应接入层。关闭开关或依赖不完整时，仍返回原厂路径。

这一层的重要边界是 **注入只属于指定进程**。蓝牙进程需要的预加载库，不能顺着环境变量传给接收端、视频进程或其他程序。启动子进程时必须清理继承的预加载环境，否则同一个库会在不匹配的进程里执行，轻则初始化失败，重则导致异常。

### 2. 使用本机当时的热点信息

手机要连接的是这台车机当前真正运行的热点，而不是某次台架测试里记下的固定网络。相关接入层从本机运行时配置取得热点信息，不能把其他车的热点密码或配对数据库打包进去。

蓝牙在这里主要负责引导；连续的媒体数据走无线网络。把两者职责分开，才能在故障时判断：是蓝牙没有完成引导，还是手机已经到达热点、但接收服务或后续会话没有起来。

### 3. 热点打开不等于已经可以接收

部分平台在原厂热点开关、网络接口状态、实际信道和接收端监听之间存在先后关系。项目中保留了经原厂 HMI 请求开启热点的路径，并等待必要网络条件。

这些步骤不能简单改成开机立刻发布“可以连接”，也不能无限等待。启动逻辑需要可观测状态、等待上限和失败退出，防止一个条件长期不成立时拖住整套蓝牙或 HMI。

## 五、无线网络：不只检查“同一个 Wi-Fi”

### 1. 配置里的信道与实际运行信道可能不同

同一套无线硬件可能同时承担热点和车机上网接口。配置文件里保存的信道，不一定就是热点当前使用的信道。

`wcp_chansync.sh` 的思路是读取实际接口状态，同步运行时配置，并提供“信道已经稳定”的状态。它不是通过强制重启无线驱动来追赶手机，也不应该把等待时间或某个固定信道当作所有平台通用的答案。

因此，“只保留一个已保存 Wi-Fi”可以排除一类干扰，但不能独自证明首次断连一定与信道无关。还需要对照实际接口、会话和启动时序。

### 2. 防火墙规则可能在原厂状态变化后重载

无线接收服务已经监听，不代表手机发来的连接一定能到达。原厂网络策略可能限制热点侧入站访问，连接管理器在网络状态变化时还可能重新加载策略。

`wcp_pf.sh` 与 `wcp_pfwatch.sh` 分别承担运行时规则准备和规则丢失后的检查。定位问题时，应区分“手机没有发起连接”“手机已经发起、但被拦截”和“接收端已经接到连接、但媒体没有建立”。这几类故障在中控上都可能只表现为转圈。

这里仍有必须如实保留的风险：继承脚本中存在基于原厂规则文件重新加载的行为，不能据此宣称任意第三方自定义防火墙都能无损共存。此类网络策略、启动重复调用及个别首次断连，仍需要针对现场日志验证，不能靠离线文件检查宣布彻底解决。

## 六、接收与显示：把媒体送到正确的通路

### 1. 接收端与视频进程各司其职

无线接收端负责会话和媒体接收，视频进程负责解码及向显示系统提交画面。原厂 HMI 还需要进入合适的 CarPlay 显示状态，触控也需要回传到相应会话。

所以我们分别检查输入、解码/渲染与实际发布状态，而不是只看某一个进程是否还活着。正常退出的进程、存在的 PID 文件、保存着最后一帧的缓冲区，都不能直接当作画面持续更新的证据。

### 2. 主屏与仪表不能靠一个全局标志区分

实际定位过的一类连接故障是：手机会话已经建立，但主屏的视频被错误分类到另一条画面通路，主屏收不到需要的内容，HMI 因而一直等不到完整的连接成功状态。

`stream_identity.c` 针对保留的接收端接口，把相关分类状态限制在线程范围，避免不同画面构造过程相互污染。普通调用仍走原有实现，不凭空生成会话或视频数据。

这是并发归属问题，不是简单把“连接超时”延长就能解决的问题。它也说明，主屏与仪表即使复用了部分协议接口，状态归属仍然必须分开。

### 3. 精确接口守卫与耦合校验

`receiver_interface.c`、`receiver_hooks.S` 和启动包装器只针对已核对的接收程序接口工作。加载前校验程序及依赖，运行时检查预期接口形态，遇到未知组合停止接入，而不是假定另一个固件的内存布局相同。

这套做法不是给未知车机强刷的理由。它的作用恰好相反：让不匹配的组合尽早停在可回退的边界。

## 七、帧率申请与位置声明：说明方法，不公开参数

这部分不是被忽略了，而是有意把**实现原理**与**具体产品参数**分开。

### 1. 主屏申请与仪表申请相互独立

接收端会向手机提供显示能力描述。主屏和仪表的描述对象不同，不能用一个全局档位同时覆盖所有输出，也不能把界面刷新调度与手机输出视频的申请混为一谈。

处理时只修改已经识别的目标显示对象；其他对象、未知类型和非目标字段保持原样。新对象构造失败时不能留下半写入的描述，更不能破坏原始对象的引用和生命周期。

### 2. 像素范围、物理尺寸与安全区域必须一致

画面偏移、拉伸或导航开启后跳位，可能来自能力描述之间不一致，并不一定是渲染器画错了。

我们区分编码画面、物理尺寸、视图区域和安全区域；地图、导航场景与卡片状态使用相互匹配的声明。不能用裁掉一部分画面来掩盖声明错误，也不能把不同仪表的显示边界直接互换。

当前精简包只保留一个手机位置配置。旧手机配置的名称只可能出现在升级识别或兼容转发里，不意味着仍提供另一套可选择的显示声明。

### 3. 申请成功不等于实际达到

手机是否持续输出、无线传输节奏、关键帧、解码提交和仪表消费能力，是连续但不同的环节。静止画面也可能按需更新。

所以声明检查、动态画面采样与实际视觉体验必须分别记录。本文不把申请值写成已经测得的显示帧率，也不以主屏流畅推导仪表一定同样流畅。

### 4. 模式切换需要真正恢复可解码的流

镜像切回地图时，接收端与消费者需要重新取得合适的关键帧和配置。只把窗口重新显示出来，有时只是恢复了一个表面状态，画面仍需等后续刷新才能出现。

`wireless_791_entry.c` 保留会话和帧流的归属，并在有效模式边沿请求恢复所需的帧。它不是不断重启接收器，也不是无限重复请求关键帧。

## 八、原厂界面：从“看得见入口”到“状态真的一致”

### 1. 原生页面与控制器生命周期

自定义页面如果只把控件画在上面，却没有正确接入原生列表、控制器、弹出层和页面生命周期，可能出现下拉框能弹出但点不了、旧遮罩吞触摸、返回后页面状态不同步等现象。

`IndependentMenuViewBridge.java` 与相应生命周期适配代码，需要在原生页面结构里建立入口、控制选择状态，并在退出时释放本页的监听和临时层。页面过渡动画也要配合原厂页面逻辑，不能把缺失动画简单理解成硬件慢。

后续测试中，设置入口响应、菜单动画、触摸及弹窗修订是分批验收的，不因为一个分支通过就把其他分支一起当作完成。

### 2. 设备出现、选择连接与会话接受是不同状态

`PhoneConnectionRuntime.java` 区分显式连接请求、已接受会话、被拒绝的会话和手动断开。`WirelessClusterGrant.java` 进一步约束仪表接管必须属于当前被接受的会话。

这解决的是“手机刚出现在设备卡片中，还没真正连接就启动了衍生显示”的状态混淆。反过来，手动断开后也不能由后台自动进入逻辑立即把用户的操作抵消。

连接确认弹窗同样不能只靠搜索一个固定文本来拦截。应识别当前正在选择的无线设备及本次连接事件，避免误拦原厂其他手机协议，或在切换分支后把旧弹窗重新带回来。

## 九、有线与无线切换：共享能力，不共享错误的所有权

### 1. 有线逻辑可以复用，但输入生命周期不能照抄

USB 接收程序和无线接收程序的上层目标相近，但它们出现、退出和重新创建输入的时机不同。共享文件名、缓存或状态，不代表可以让双方随时覆盖彼此。

曾出现过有线切回无线后，原有解析进程还在，但新的输入不再正确写入的情况。修复重点在输入所有权、文件被替换后的处理和新会话重新订阅，而不是每次都把全部程序杀掉重装。

这也解释了为什么“有线已经做好”能够成为重要参考，却不能保证把启动路径改成无线后，所有衍生功能会自动成立。

### 2. 兼容层只作用于指定程序

`TransportLease.java`、`transport_shim.c` 通过短期状态协调已核对的无线程序。它们不应让原厂驱动、SSH 或其他项目以为物理 USB 不存在。

USB 仍连接着时，用户主动断开有线后再选无线，仍有需要单独保留的边界。不能把这个局部操作序列的问题，扩大成全系统隐藏 USB 的理由。

## 十、仪表地图与镜像：在无线基础上继续接入

无线地图输入、镜像采集、渲染启动条件和地图/镜像切换，是不同的接点。

一个典型修复是：无线画面已经在持续产生，但渲染启动条件仍只认有线投屏程序。补上当前无线会话的有效归属后，才能让已有渲染链路接纳它，而不是伪造一个有线进程标记。

另一个修复是镜像切回地图时的恢复。它需要向正确的会话请求恢复所需的帧，而不是只更改菜单文字或等待用户碰一下手机。

但 Home 后后台画面暂停、静态画面返回中控延迟恢复，与上述问题并不是同一个结论。这两项曾被明确暂缓，不能写成已经解决。音频继续播放也不代表后台视频仍在更新。

导航卡片是地图视频场景的一部分。精简交付保留卡片，并不意味着保留了独立的音乐、封面、转向、距离或到达时间文字映射模块；这些功能边界需要在版本说明中讲清楚。

## 十一、接手后最重要的工程方法

### 1. 先保存故障现场，再更改代码

转圈、黑屏、最后一帧停住、仪表退回原车地图，表面上相似，根因却可能分属不同层。处理时先保存会话、输入、输出和界面状态，再决定修改哪个接口。

出现诊断补丁导致黑屏、声音不连续等副作用时，先回退已验证版本，确认恢复，再做隔离测试。不能为了得到更多日志，把故障版本长期留在车上。

### 2. 一次验证一个变化

连接、菜单动画、镜像、卡片、地图恢复等修订分批验证。已经通过的功能建立可回退基线；后续试验留在独立副本，不因为“顺手改了一点”就混进现场测试。

这也是为什么源码构建通过、离线模拟通过和用户确认正常，要分别记录：它们回答的不是同一个问题。

### 3. 不把软件版本编号当成验收

“迭代了多少版”只能说明探索次数，不能替代稳定性证据。最终保留的是能解释问题、能回退、能重复验证的改动，而不是最大的内部编号。

## 十二、交付阶段：旧版本覆盖安装同样是研发内容

一个新版本从空白环境安装成功，不代表它可以安全覆盖所有旧版本。

这次兼容性排查发现了一个具体例子：旧开源信息模块会把原厂媒体进程替换成包装器，并把实际程序保存在项目目录中。精简版如果只删掉旧模块目录，外面的包装器就可能还指向已经消失的依赖。

因此，升级必须先识别已知旧版本和包装器，确认保存的原程序有效，再把旧接入安全退出。旧类路径、信息 JAR、备份范围、旧管理入口和失败回滚都需要一并检查，而不是只看新文件是否上传完成。

当前方案还保留了极少量旧脚本名作为更新器兼容壳。它们只转发到当前唯一配置，不提供第二个手机声明，也不重新开放旧菜单。

对未知的包装器、被其他项目修改的启动文件、错误机型的旧目录或损坏备份，正确结果是停止并保留现场，而不是“为了安装成功”强行覆盖。

## 十三、主要代码分工索引

| 代码/组件 | 主要作用 |
|---|---|
| `btstack_wrap.sh` | 把无线引导接到原厂蓝牙进程，并隔离预加载环境。 |
| `wcp_autostart.sh` | 协调网络条件、运行时文件和接收端启动。 |
| `wcp_chansync.sh` | 对照实际接口同步信道状态，不直接替代无线驱动。 |

## 十四、目前可以说到哪里

可以说明的是：我们把无线引导、原厂网络、接收端、HMI 与显示/输入链路串联起来，逐步解决了多种连接状态、画面归属、菜单交互和切换衔接问题，并把交付升级本身纳入了测试。

不能扩大成下面这些结论：

- 已适配某一款 MHI2，就等于所有大众、奥迪、斯柯达、SEAT 或 MHI2Q 都通用。
- 请求了一个视频能力档位，就等于实际消费达到了相同水平。
- 早期链路曾跑通，就等于所有版本和长期稳定性已经验收。
- 离线事务与模拟测试通过，就等于新的精简组合已经完成真实手机和实车验收。
- 首次连接断连、后台视频暂停或自定义网络策略的所有边界，都已经有确定结论。

当前还应继续保留真实场景测试：冷启动首次连接、反复重连、有线/无线切换、原车雷达与倒车共存、后台显示边界，以及精确固件的升级和恢复。
